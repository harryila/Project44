# RUNS.md: every training run and where its evidence is

One row per training run that left any trace in this export (a checkpoint, a training curve, an
hparams.yaml, a GPU-box log, or an evaluation JSON). Every cell is taken from a file in this
repository; where a file does not say, the cell says `unknown`. Paths are relative to the
repository root. The three live models come first, then the rest grouped by line of work.

## How to read the table

- **init checkpoint**: `from scratch`, `released` (the upstream `MIDI2ScoreTF.ckpt`), or the own run
  whose checkpoint was warm-started from.
- **recipe**: the launcher script in `scripts/` and the `train.py fit` flags it passes. When no
  launcher survives, the flags come from the report or from the training log.
- **data**: the manifest or corpus the loader read. `ASAP` always means the 822 aligned training
  performances of the pinned `asap-dataset` (quickstart asset `asap-dataset-8cba199e-with-chunks.tar.zst`).
- **kept checkpoint**: the asset name in `assets/ASSETS.csv` (quickstart tier or `ckpt-archive/...`),
  or `NONE SURVIVES`. The `contents` column of that CSV lists every original path of each file.
- **curve**: the Lightning `metrics.csv` of the run. `benchmark/curves/<run>.metrics.csv` is a byte
  identical copy of `legacy/checkpoints_backup/gpu_full/<run>/lightning_logs/version_0/metrics.csv`
  (checked with md5). Epoch and step numbers quoted here are read from those files.
- **config**: the `hparams.yaml` Lightning wrote next to the curve. **Caveat for warm-started runs:**
  `train.py` loads the init checkpoint with `load_pretrained_init` and then overrides learning rate,
  warmup, total steps and tuplet weight as private attributes (`train.py` lines 698 to 727), so the
  `hparams.yaml` of every warm-started run records the stored defaults (`learning_rate 0.0003`,
  `total_steps 40000`, `warmup_steps 1000`, `tuplet_weight 1.0`) and not the flags actually used.
  For those runs trust the launcher script and the log, not the YAML. From-scratch runs go through
  `_new_model(...)` and their YAML is accurate.
- **evaluation**: the JSON file, the headline number and the pad threshold. Three harnesses exist:
  1. `benchmark/eval_padsweep.py` (files with `ckpt`, `thresholds`, `results` and a `per_threshold`
     map per piece): one performance per piece on the 14-piece ASAP test set; the "corpus MeanER @0.50"
     is the mean of `results[*].per_threshold["0.50"].MeanER`. The number of pieces that actually scored
     is given in brackets when it is not 14 (music21 timeouts drop pieces). `scripts/run_padsweep.sh`
     and `scripts/rerank_by_muster.sh` drive it.
  2. `benchmark/eval_tier1_asap.py` (files with `meta`, `aggregate`, `per_performance`): all 59
     test performances; the number is `aggregate.muster.MeanER`.
  3. `benchmark/eval_tuplet.py` (files with `ckpt` and `results` only, one `MeanER`, `pred_tuplets`
     and `tuplet_ratio` per piece, no `thresholds`): with a `--pieces` filter it scores the five
     hard-tail pieces Scriabin, Mozart, Liszt, Ravel, Prokofiev (the `benchmark/tuplet_*.json` and
     `benchmark/_ar*.json` files). The reports quote a four-piece mean that excludes Prokofiev; both
     are given.
- **outcome**: one phrase, taken from the report that concluded the run.
- Validation loss (`val/total`) and MUSTER disagree repeatedly (for example `ssl_bigc` has the best
  val of all masked-SSL runs and a worse MUSTER; the bidirectional `scratch_*` runs reach far lower
  val and generate nothing). Pick checkpoints by MUSTER; `scripts/rerank_by_muster.sh`
  exists for that.

## 4. The triplet-placement experiments (June 7 to 9, 2026)

These runs have a GPU-box training log in `legacy/benchmark/box_logs/` but no report of their own;
the only narrative is the matrix in `LAB_REPORT_COMPLETE.md` section 7.3. The placement diagnostic
(`legacy/benchmark/box_logs/diag_*.log`, Scriabin, 1,408 predicted onsets, ground truth 66 of 1,382 at
triplet phases = 4.78 percent) gave 0 onsets at triplet phases for most of them; the exceptions are
`ssl_balanced` (280, 19.9 percent, over-shoot), `ssl_bal_g1.0` (20, 1.4 percent), `ssl_pseudo` (13,
0.9 percent) and `ssl_b2` (1). None of the training logs prints the init checkpoint path (the line
"AUTOREGRESSIVE (causal decoder) from-scratch training ON" is printed by `train.py` for every
`--autoregressive` run, warm-started or not, so it is not evidence either way). Their epoch-0 validation losses (0.49 to 0.53) are only reachable
by a warm start (a from-scratch run starts above 1.0), and the warmup 300 and 15-epoch settings
match the `run_ssl_tuplet.sh` defaults whose default init is `ssl_classical_clean` epoch 13; that
inference is marked "(inferred)". Unpaired-score counts are what the loader printed.
