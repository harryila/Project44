# scripts/: what each file is, whether it still runs, and what it needs

This directory holds four kinds of files, and the status column tells them apart:

| Status | Meaning |
|---|---|
| CURRENT | Runs from this repository layout as written, given the inputs in the last column. |
| HISTORICAL | Ran only on the rented GPU box in 2026. Hard-coded box paths, fixed GPU ids, or `pkill` of other jobs. Kept as the record of how a run was launched. Most carry a `# HISTORICAL:` banner as their first header line; the few without one are marked and explained in the table. Do not run as is. |
| FROZEN | Hash-pinned research script. Its sha256 is recorded in `research/supplement/PROVENANCE.md` (or, for the two metric modules, in `research/supplement/MANIFEST.sha256` and in the `metric` block of the result JSONs). Every result in `benchmark/` that names the best-of-N / support-selection study was produced by these exact bytes. **Must not be edited.** Copy to a new file name if you want to change anything. |
| SUPERSEDED | Replaced by a later script; the table says by what. Kept so the failed version stays auditable. |

Two facts that bite every script that touches the model: the tokenization cache is only hit when the loader sees the literal data dir `./data/` after `cd MIDI2ScoreTransformer` (the portable launchers do this for you), and Apple MPS must never be used for Block 2 (`musicml_paths.device()` returns cuda or cpu).

## The portable launchers

`_env.sh`, `run_ssl_classical_clean.sh` and `run_ssl_tuplet.sh` are the three files to start from if you train. `_env.sh` is sourced by the other two: it sets `REPO`, `PY` (the `venv311` interpreter if present, otherwise `python3`), `MUSICML_GPU` (default 0), `LOG_DIR` and `PYTHONPATH`, and it refuses to start if another `train.py fit` is already running unless `KILL_EXISTING=1`. Override any of these with environment variables; `MUSICML_ROOT` relocates the whole tree.

The best own model was produced with

```bash
TUPLET_WEIGHT=2.0 STAGE=ssl_tuplet20 bash scripts/run_ssl_tuplet.sh
```

(the defaults inside the script, weight 5.0 and stage `ssl_tuplet5`, are the sweep's starting point, not the best run; the sweep was U-shaped: weight 5.0 gave 13.04, 2.5 gave 12.45, 2.0 gave 11.87, see `docs/reports/LAB_REPORT.md` section 11). Both launchers need the classical_clean renders and cache pickles that `data/pairs_classical_clean_manifest.csv` points to, and those are **MISSING** (they never left the GPU box; only the manifest is tracked). Rebuilding them from `PDMX` with `build_classical_unpaired.py` then `build_classical_clean_manifest.py` produces a new dataset version, not a byte-identical one.

## The research chain: best-of-N / support-selection study

These scripts form one dependency chain, each importing the previous ones as modules (run them from the repository root; each script puts `scripts/` and the model package on its own import path, and every selector and runner inherits CPU FP32 deterministic decoding from `verifier_bestofn.py`, which in turn imports `muster_tuplet_decompose.py`). Their docstrings cite protocol documents by their old paths `paper/bestofn_prereg.md`, `paper/REVISION_LOCALITY_PROTOCOL.md` and the audit notes; those documents now live under `research/protocols/` (`bestofn_prereg.md`, `REVISION_LOCALITY_PROTOCOL.md`, `V10_1_CONFIRMATORY_AUDIT.md`, `V10_1_ORACLE_AUDIT.md`), and the hash ledger is `research/supplement/PROVENANCE.md`.

How they chain. `verifier_bestofn.py` (V1 to V3b) is the base: it samples N rhythm-stream candidates from the model, defines the rhythm-algebra verifier and the MUSTER-plus-tuplet-decomposition evaluation, and every later script reuses its environment, decode and scoring functions. `local_repair_v4.py` (V4) splices donor windows into the greedy decode; `local_repair_v5.py` is the exploratory follow-up after V4's detector saturated. `likelihood_timing_selector_v6.py` (V6) returns to whole-candidate selection with a teacher-forced rhythm loss plus timing evidence; `evidence_screen_selector_v7.py` (V7) screens by timing evidence first; `guarded_selector_v8.py` (V8) adds the keep-count and model-loss guards and lets the baseline compete. `decode_lever_sweep_v9.py` (V9) tests deterministic decode-time levers (offset phase boost, the A1/A2 duration priors) as a way to create a better pool. `routed_selector_v10.py` (V10, frozen as V10.1) routes per piece between baseline, the deterministic phase-duration candidate, and guarded best-of-N. `confirmatory_v10_1.py` runs V10.1 on the ten untouched pieces in two phases (ground-truth-blind selection, then evaluation with stream-hash verification). `oracle_prefix_v10_1.py` evaluates all 256 locked candidates and the prefix oracles after the fact; `revision_locality_v10_1.py` describes how far the oracle candidates are from the greedy decode in aligned streams. `tuplet_metrics_v2.py` (the exact TPF adapter) and `muster_tuplet_decompose.py` (the MUSTER per-note decomposition joined to exact MusicXML `<time-modification>` tags) are the metric modules under all of it; the earlier TPQN=24 labeler was found invalid and its outputs are kept as `*_invalid_tpqn24.json`. The `audit_*` scripts are read-only: they re-derive the headline arithmetic from the result JSONs and, in this repository's versions, also verify the frozen hashes of the scripts, the prior and the released checkpoint.

All of them need `released`, `ASAP`, `MUSTER` and, for the exploratory selectors, several hours of CPU; the frozen ones additionally need `data/duration_priors.pt` (tracked) and, to re-read rather than regenerate candidate pools, the `work dirs`. Outputs are listed file by file in `benchmark/README.md`.
